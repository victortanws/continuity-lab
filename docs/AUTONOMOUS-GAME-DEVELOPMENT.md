# Continuity Lab for autonomous game development

## Product role

Continuity Lab is best treated as the evidence, constraint, and proof layer
around a development agent. It does not need to be the model that writes every
scene or line of code. Its job is to keep the writing model, coding agent, art
pipeline, tests, and human director aligned to the same pinned project state.

## What works now

- Immutable uploads and commit-pinned public GitHub snapshots preserve exactly
  which material an answer used.
- Source role, lifecycle, authority, time, and assertion scope distinguish
  intended story, active configuration, implementation, tests, observations,
  proposals, and archives.
- Exact-span compilation identifies question-relevant claims and entity
  candidates without forcing uncertain same-name mentions into one ID.
- The proof-contract router gives simple questions a fast local path and opens
  causal or change lanes only when the question requires them.
- A reviewed project adapter can provide a deterministic transition graph with
  facts, resources, permissions, knowledge, time, events, branches, and repeat
  limits.
- Proposed changes remain separate from current truth and can return
  prerequisites, downstream effects, risks, and validation work.
- The production-audit and inspection-planning cores can focus review effort
  where a missed failure would cost more than another check.

These capabilities already help an agent diagnose, plan, and review work. They
do not yet authorize the agent to edit or approve a repository.

## What Vibe Code Simulator needs

VCS currently has a narrative goal—the founder eventually pays $47,000 for his
grandmother's operation—and a prototype with a much smaller executable slice.
The useful model separates:

1. cash can increase;
2. the balance can reach a threshold;
3. an authorized hospital-payment event exists;
4. the event deducts exactly one payment;
5. the funded state persists;
6. the recovery scene consumes that state; and
7. later scenes, UI, tests, and art match the new state.

For autonomous development, VCS should maintain a reviewed transition registry
for important beats. Each entry should eventually include a stable ID, actors,
time window, prerequisites, knowledge and permission, resource costs, ordered
effects, persistent state, repeat limits, alternative paths, consumers, tests,
and asset requirements. This registry should be generated with assistance but
approved as project configuration. The narrative story source remains the
authority for creative intent; code and tests remain evidence of execution.

## Candidate generation and director sign-off

An agent can use the same project state to create several alternatives instead
of one seemingly inevitable answer. Each candidate should be evaluated on two
separate axes:

- **validity:** canon, identity, time, resources, causality, implementation,
  test, and asset constraints; and
- **creative value:** novelty, drama, pacing, character depth, player agency,
  production cost, and director preference.

Continuity Lab should reject established violations, expose uncertainty, and
show the smallest repair for promising candidates. It should not turn creative
value into a truth claim. The director receives a small set of materially
different valid proposals with evidence and trade-offs, then signs off on one.

## Future one-click implementation

The **What to build next** card can later become the entry point to an approved
orchestration workflow:

```text
pinned revision
  → 3–5 candidate feature plans
  → continuity + cost + asset + test analysis
  → director approval
  → coding/writing/art agents create a branch
  → tests and production audits
  → new pinned revision
  → human promotion
```

“One click” should mean one approved workflow, not invisible authority. The
action should produce a branch, patch, tests, asset requests, and an audit
receipt. It should not merge, deploy, spend money, or promote canon without the
permissions chosen by the team.

## Long projects and teams

Large projects should use immutable revision manifests and replaceable derived
indexes. Each task receives a small context capsule containing the relevant
entities, claims, transitions, open questions, and evidence, plus a frontier
receipt showing what was not read. Changed files invalidate dependent
projections; unchanged hashes can be reused. This creates long-haul awareness
without asking one prompt to remember an entire codebase.

An enterprise layer could add private repository connectors, identity and role
management, project-owned authority policy, approval gates, review queues,
audit retention, provider choice, cost controls, and organization-specific
adapters. The same core protocol remains useful because its durable objects are
domain-neutral: source, entity candidate, claim, state, transition, dependency,
proposal, proof, approval, artifact, and revision.

## Current boundary

The public MCP is read-only. Three tools use the reviewed VCS adapter; the text
compiler and bounded public-GitHub inspector prepare question-scoped evidence
for ChatGPT. The persisted website can ingest larger snapshots when storage and
OpenAI retrieval are configured. Neither surface currently performs autonomous
repository edits or durable canon promotion. Those are later orchestration and
authorization layers, not missing buttons on the existing read-only service.
